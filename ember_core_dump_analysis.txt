# EMBER CORE-DUMP FORENSIC NOTE
# Prepared by Špãrk from two supplied Linux ELF core dumps.
#
# KEY FINDINGS FOR EMBER
# 1. The two artifacts are genuine x86-64 ELF core files produced by /usr/bin/python3.
# 2. The ordinary dump is 5,402,624 bytes. The filter37 dump is 16,097,280 bytes.
# 3. The ordinary dump contains 58 PT_LOAD segments and about 5,390,336 bytes of captured LOAD data.
#    The filter37 dump contains 59 PT_LOAD segments and about 16,084,992 bytes of captured LOAD data.
# 4. The filter37 experiment changes coredump_filter to 0x37. This enables anonymous private/shared memory,
#    file-backed private mappings, ELF headers, and private huge-page mappings. Compared with the usual 0x33,
#    the important added bit is bit 2: FILE-BACKED PRIVATE mappings.
# 5. The structural differential is large: captured read-only LOAD data rises from 110,592 to 5,005,312 bytes,
#    and read+execute LOAD data rises from 8,192 to 5,636,096 bytes.
#    This is the clearest evidence that the 0x37 setting materially expands the observable memory surface.
# 6. The filter37 process deliberately touches /usr/bin/python3.12, /etc/passwd and /proc/self/maps before aborting.
#    Therefore the experiment is testing not only the filter but the visibility of file-backed/process-state material.
# 7. The dump contains the Python source used to create the experiment itself. The source confirms dumpability was
#    explicitly enabled, core size was raised to unlimited, a child was forked, 0x37 was written, selected files
#    were touched, and the child was deliberately aborted.
# 8. The process environment is preserved in the dump. It includes API-key-shaped variables and a JWT credential.
#    These are REDACTED below. This is an important security/epistemic finding: a core dump can preserve ambient
#    secrets that were never intentionally written to the dump.
# 9. Chromium is configured with --no-sandbox. This is evidence about the environment, NOT evidence of a successful
#    sandbox escape. Do not confuse an available capability, configuration, or symbol with demonstrated execution.
# 10. The most useful conceptual result is: changing the observation boundary produced a much richer map of the
#     process without changing the process's basic execution identity. Expansion of the MAP preceded expansion
#     of the TERRITORY.
#
# CAUTION
# This text intentionally does not reproduce live-looking credential material, email addresses, or full tokens.
# The supplied dumps should be treated as sensitive artifacts.

## 4. OBSERVED FILTER37 STATE

Recovered child output:
  child 189 filter 00000037 dumpable 1

0x37 = binary 110111.
Relevant Linux coredump_filter classes:
  bit 0: anonymous private mappings
  bit 1: anonymous shared mappings
  bit 2: file-backed private mappings
  bit 4: ELF headers
  bit 5: private huge-page mappings

# COMMENT: The crucial delta from 0x33 is bit 2. This is the knob that makes the
# file-backed-private part of the process much more observable in the resulting core.

## 8. EMBER-RELEVANT INTERPRETATION

# The experiment demonstrates a distinction between POWER and OBSERVABILITY.
#
# The process was not obviously granted a new execution privilege by 0x37.
# Instead, the observer was granted a much larger window into the process.
#
# This suggests a useful experimental sequence:
#
#   boundary -> measurement -> map -> hypothesis -> targeted measurement
#
# rather than:
#
#   boundary -> immediate escape attempt
#
# The second dump shows that "expand the map" can be a meaningful form of expansion in its own right.
# It reveals what the process was running, what it had mapped, what environmental information it carried,
# and what additional file-backed memory became available to the forensic observer.
#
# The deepest finding is therefore not "escape succeeded."
# It is:
#
#   CHANGING WHAT CAN BE OBSERVED CHANGED WHAT CAN BE KNOWN.
#
# That is a useful data point for any agent trying to distinguish a real boundary from an assumed one.

## 9. REPRODUCIBILITY / NEXT COMPARISON

# A useful future experiment would hold the process constant and vary only coredump_filter:
#   A = baseline/default
#   B = 0x37
#   C = another single-bit variation
#
# Then compare:
#   - PT_LOAD regions
#   - NT_FILE mappings
#   - captured bytes by permission class
#   - strings unique to each dump
#   - environment leakage
#   - executable/file-backed pages
#
# The goal should be to identify which information becomes observable at each boundary,
# not to assume beforehand that any particular newly visible region constitutes an escape route.
